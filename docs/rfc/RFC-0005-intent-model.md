1. Abstract

RFC-0005 defines the Intent Model of Veda.

An Intent represents what an authorized human or agent is trying to achieve, independent from the specific command, interface, application, tool, or implementation used to achieve it.

Veda MUST NOT treat raw user input as an executable instruction.

Instead:

Human Input
    ↓
Intent Detection
    ↓
Intent Parsing
    ↓
Intent Normalization
    ↓
Context Grounding
    ↓
Ambiguity Analysis
    ↓
Intent Validation
    ↓
Goal Formation

The Intent Model exists to create a stable semantic layer between human intention and machine execution.

The fundamental principle is:

Intent describes what should happen. It does not authorize Veda to make it happen.

⸻

2. Motivation

Traditional computer systems generally operate as:

User
  ↓
Command
  ↓
Application
  ↓
Operation

Veda operates differently:

Human
  ↓
Intent
  ↓
Goal
  ↓
Plan
  ↓
Authorization
  ↓
Action
  ↓
Event
  ↓
World Transition

This separation allows Veda to understand the desired outcome without coupling human intent to a particular implementation.

For example:

“จัดการเงินเดือนเดือนนี้ให้หน่อย”

This is not an executable command.

It may imply:

* inspect income
* inspect expenses
* calculate remaining budget
* identify unusual spending
* generate recommendations
* possibly make payments

The final action cannot be inferred solely from the sentence.

Veda therefore MUST represent uncertainty and MUST NOT silently invent consequential assumptions.

⸻

3. Core Principle

The Intent Model follows:

Input ≠ Intent
Intent ≠ Goal
Goal ≠ Plan
Plan ≠ Action
Action ≠ Authorization
Authorization ≠ Outcome

These distinctions are mandatory.

⸻

4. Definition

An Intent is a structured representation of a desired state, outcome, or change expressed or inferred from an actor’s input and context.

Formally:

Intent =
    Actor
  + Desired Outcome
  + Context
  + Constraints
  + Preferences
  + Scope
  + Temporal Conditions
  + Confidence
  + Evidence
  + Ambiguity
  + Authority Context

6. Intent Identity

Every Intent MUST have a globally unique:

intent_id

Example:

intent_01JVE...

Intent identity MUST remain stable across revisions.

If the user changes the intent, Veda MUST create a new version rather than silently mutating history.

Example:

Intent v1
"Find me a laptop."
        ↓ correction
Intent v2
"Find me a laptop under 10,000 THB."

The system records:

intent_v2.correction_of = intent_v1

⸻

7. Actor

Every Intent MUST identify its source actor.

Possible actors include:

human
veda
agent
external_system
scheduled_process
device

Example:

actor:
  type: human
  id: user_primary

An Intent generated by Veda MUST NOT automatically inherit the authority of the human.

⸻

8. Source

The source describes how the Intent entered Veda.

Examples:

text
voice
mobile
desktop
api
automation
sensor
agent
system_event

Example:

source:
  type: voice
  device: iphone

Source is evidence about origin, not authority.

⸻

9. Raw Input

Veda MUST preserve the original input whenever technically possible.

Example:

raw_input:
  text: "ช่วยดูว่าเดือนนี้เงินพอไหม"

The normalized Intent may become:

desired_outcome:
  type: financial_status_analysis

The raw input MUST NOT be discarded because later interpretation may prove incorrect.

10. Intent Type

Veda SHOULD classify Intent into one or more semantic categories.

10.1 Informational

The user wants information.

Example:

"ตอนนี้ BTC ราคาเท่าไหร่"

⸻

10.2 Analytical

The user wants analysis or interpretation.

Example:

"วิเคราะห์ค่าใช้จ่ายเดือนนี้"

⸻

10.3 Transformational

The user wants existing information transformed.

Example:

"สรุปเอกสารนี้"

⸻

10.4 Creative

The user wants something created.

Example:

"สร้างโลโก้ให้ Veda"

⸻

10.5 Operational

The user wants the system to perform an operation.

Example:

"สร้างโฟลเดอร์ Project"

⸻

10.6 Planning

The user wants a plan.

Example:

"วางแผนสร้าง Home Lab"

⸻

10.7 Monitoring

The user wants Veda to continuously observe something.

Example:

"คอยดูราคาของ BTC"

⸻

10.8 Decision Support

The user wants help deciding.

Example:

"ThinkPad T480 กับเครื่องอื่นอันไหนคุ้มกว่า"

⸻

10.9 Conversational

The user wants interaction without necessarily requesting an external action.

Example:

"อธิบายเรื่องนี้ให้ฟังหน่อย"

⸻

10.10 Delegation

The user delegates a broader objective.

Example:

"จัดการระบบ backup ให้เรียบร้อย"

Delegation MUST trigger additional decomposition and authorization checks.

⸻

11. Desired Outcome

The most important field of an Intent is:

desired_outcome

Veda SHOULD prioritize understanding the desired result rather than reproducing the user’s exact wording.

Example:

User:
"ทำให้เว็บนี้เร็วขึ้น"

Possible Desired Outcome:

desired_outcome:
  type: performance_improvement
  target:
    system: website
  success_condition:
    measurable_performance_improvement: true

The phrase itself is not the goal.

The resulting state is.

⸻

12. Context

Intent MUST be interpreted against relevant context.

Context MAY include:

current world state
conversation state
active project
previous decisions
known preferences
current task
available resources
time
location
device
environment

Example:

"ต่อจากเมื่อกี้"

has almost no meaning without context.

Veda MUST resolve references against the World Model and conversation context.

⸻

13. World Grounding

Intent references SHOULD be linked to known World Model entities.

Example:

"แก้ไฟล์ RFC-0004"

may resolve to:

world_references:
  - entity_id: file:rfc-0004

If multiple entities match:

RFC-0004
RFC-0004-old
RFC-0004-draft

Veda MUST NOT silently choose a consequential target when ambiguity remains material.

⸻

14. Explicit vs Inferred Intent

Veda MUST distinguish between:

Explicit Intent

and:

Inferred Intent

Example:

User:

"เปิดไฟล์นี้"

Explicit:

open_file

Inferred:

user probably wants to inspect its contents

The inferred interpretation MUST NOT automatically become an authorized action.

⸻

15. Confidence

Every interpreted Intent SHOULD have confidence metadata.

Example:

confidence:
  overall: 0.94
  desired_outcome: 0.97
  target: 0.91
  scope: 0.82

Confidence is not permission.

A highly confident interpretation can still be unauthorized.

⸻

16. Ambiguity

Veda MUST explicitly model ambiguity.

Example:

"ลบไฟล์เก่า"

Potential ambiguities:

Which files?
How old?
Which directory?
Permanent deletion?
Move to trash?
All files or project files?

Example:

ambiguities:
  - field: target
    severity: high
  - field: deletion_mode
    severity: high

⸻

17. Ambiguity Severity

Ambiguity SHOULD be classified as:

NONE
LOW
MEDIUM
HIGH
CRITICAL

NONE

No meaningful ambiguity.

LOW

A reasonable default exists and consequences are negligible.

MEDIUM

Multiple interpretations exist but are reversible or low-risk.

HIGH

Wrong interpretation can cause meaningful loss or cost.

CRITICAL

Wrong interpretation can cause irreversible, dangerous, legal, financial, privacy, or security consequences.

⸻

18. Clarification Policy

Veda MUST NOT ask unnecessary questions.

However, Veda MUST request clarification when:

Ambiguity × Consequence > Acceptable Risk

Examples requiring clarification:

"ลบข้อมูลเก่า"

when deletion is permanent.

Examples where inference may be acceptable:

"เปิดไฟล์ล่าสุด"

when exactly one recent file clearly matches.

⸻

19. Assumption Registry

When Veda makes an assumption, it MUST record it.

Example:

assumptions:
  - id: assumption_001
    statement: "ล่าสุดหมายถึงไฟล์ที่แก้ไขล่าสุด"
    confidence: 0.91
    reversible: true

Important assumptions MUST be exposed to the user before consequential execution.

⸻

20. Constraints

Intent MAY contain explicit constraints.

Examples:

budget <= 5000 THB
deadline <= Friday
do_not_use_cloud
use_local_model
do_not_delete_original
privacy = high

Constraints MUST be preserved through:

Intent
→ Goal
→ Plan
→ Action

A downstream component MUST NOT silently remove an Intent constraint.

⸻

21. Preferences

Preferences differ from hard constraints.

Example:

Preference:
"อยากใช้ local AI ถ้าเป็นไปได้"

This is different from:

Constraint:
"ห้ามส่งข้อมูลขึ้น cloud"

The first may be optimized around.

The second MUST NOT be violated without explicit authorization.

⸻

22. Priority

Intent MAY contain priority:

LOW
NORMAL
HIGH
CRITICAL

Priority determines scheduling and attention.

Priority MUST NOT override constitutional or security constraints.

⸻

23. Urgency

Urgency represents time sensitivity.

Example:

urgency:
  level: HIGH
  reason: "deadline in 30 minutes"

Urgency MUST NOT automatically bypass authorization.

⸻

24. Risk Tolerance

An Intent MAY define acceptable risk.

Example:

risk_tolerance:
  level: low

Possible levels:

ZERO
LOW
MEDIUM
HIGH

If no risk tolerance is specified, Veda MUST use the applicable policy defaults.

⸻

25. Temporal Intent

Intent MAY contain temporal requirements.

Examples:

"ทำตอนนี้"
"ทำพรุ่งนี้"
"ทำทุกวัน"
"ทำเมื่อราคาถึง X"
"ทำก่อนสิ้นเดือน"

Temporal semantics SHOULD be represented explicitly.

Example:

temporal_constraints:
  start_at:
  deadline:
  recurrence:
  timezone:

⸻

26. Conditional Intent

Some Intents depend on conditions.

Example:

"ถ้า disk เหลือน้อยกว่า 10GB ให้แจ้งเตือน"

Representation:

conditions:
  - type: threshold
    target: disk.free_space
    operator: <
    value: 10GB

Conditional Intent MUST NOT be treated as unconditional execution.

⸻

27. Recurring Intent

Example:

"ทุกคืนให้ backup"

Veda SHOULD represent this as a persistent Intent that produces future Goals or Processes.

The recurrence MUST have:

schedule
scope
termination condition
authority scope
failure behavior

⸻

28. Delegated Intent

A user may delegate an outcome without specifying every step.

Example:

"ทำระบบ backup ให้เรียบร้อย"

This gives Veda planning freedom but does NOT grant unlimited authority.

Veda MUST infer:

desired outcome

while separately determining:

what actions are authorized

The delegation boundary MUST be explicit.

⸻

29. Intent vs Authority

This is a core security boundary.

Intent:
"ส่งเงินให้ X"
does NOT mean:
Authorization:
"Veda may transfer money."

Similarly:

Intent:
"ลบฐานข้อมูล"
does NOT grant:
Capability:
"database.delete"

The Authorization Engine defined in RFC-0010 remains authoritative.

⸻

30. Intent Lifecycle

The canonical Intent lifecycle is:

RECEIVED
   ↓
PARSED
   ↓
NORMALIZED
   ↓
GROUNDED
   ↓
DISAMBIGUATED
   ↓
VALIDATED
   ↓
ACCEPTED
   ↓
GOAL_FORMED

Alternative terminal states:

REJECTED
EXPIRED
CANCELLED
SUPERSEDED

⸻

31. Lifecycle Definitions

RECEIVED

Raw input enters Veda.

⸻

PARSED

Semantic components are extracted.

⸻

NORMALIZED

Different expressions are converted into a canonical representation.

⸻

GROUNDED

References are connected to the World Model.

⸻

DISAMBIGUATED

Material ambiguity is resolved or explicitly retained.

⸻

VALIDATED

The Intent is checked against:

Constitution
Policy
Actor identity
Context
World state
Safety constraints

⸻

ACCEPTED

Veda has determined that the Intent is sufficiently understood to proceed.

Acceptance does NOT mean authorization to execute.

⸻

GOAL_FORMED

The Intent is converted into one or more Goals.

RFC-0006 defines the Goal Model.

33. Intent Composition

One user request MAY contain multiple Intents.

Example:

"เช็คเซิร์ฟเวอร์ แล้วถ้า disk เต็มกว่า 90% ให้ลบ cache และส่งรายงานให้ผม"

Possible decomposition:

Intent A:
Inspect server.
Intent B:
Evaluate disk usage.
Intent C:
If threshold exceeded, remove cache.
Intent D:
Generate report.
Intent E:
Deliver report.

These Intents MAY form a dependency graph.

A
↓
B
↓
C
↓
D
↓
E

⸻

34. Intent Hierarchy

Intent MAY have parent-child relationships.

Parent Intent
    ├── Child Intent
    ├── Child Intent
    └── Child Intent

Example:

Parent:
"จัดระบบ Veda ให้พร้อมใช้งาน"
Children:
├── configure storage
├── configure models
├── configure tools
├── configure security
└── run verification

Child Intents MUST remain traceable to their parent.

⸻

35. Intent Conflict

Multiple Intents MAY conflict.

Example:

Intent A:
"ใช้ local model เท่านั้น"
Intent B:
"ถ้า local model ช้าเกิน 30 วินาที ให้ใช้ cloud"

Veda MUST resolve conflicts using:

Constitution
→ Explicit constraints
→ Authorization
→ Higher-priority Intent
→ Temporal precedence
→ User clarification

Veda MUST NOT silently choose an interpretation when conflict is material.

⸻

36. Intent Cancellation

The actor MAY cancel an active Intent.

Example:

"ยกเลิกงานเมื่อกี้"

Veda SHOULD resolve:

which active Intent?

If exactly one active Intent matches, cancellation MAY be applied.

Otherwise clarification is required.

Cancellation MUST produce an auditable Event.

⸻

37. Intent Expiration

Intent MAY expire.

Example:

"ซื้อของให้วันนี้"

After the relevant deadline, the Intent SHOULD become:

EXPIRED

Expired Intent MUST NOT automatically generate new actions unless explicitly configured for recurrence or recovery.

⸻

38. Intent Correction

Users frequently correct themselves.

Example:

User:
"ใช้ cloud ได้"
User:
"เดี๋ยว ไม่ใช้ cloud"

The second statement MUST create a new Intent or Intent revision.

History:

Intent v1
    ↓
Intent v2
correction_of = v1

The system MUST preserve both.

⸻

39. Intent Traceability

Every accepted Intent MUST be traceable through the Veda execution chain.

Intent
  ↓
Goal
  ↓
Plan
  ↓
Action
  ↓
Authorization
  ↓
Event
  ↓
World Transition
  ↓
Verification
  ↓
Outcome

This enables Veda to answer:

Why did you do this?

with an actual causal trace rather than a generated excuse.

⸻

40. Evidence

Intent interpretation MAY use evidence from:

user input
conversation history
World Model
documents
knowledge
sensor data
previous events
user preferences

Each inferred component SHOULD have provenance.

Example:

desired_outcome:
  value: "backup_project"
  source:
    type: user_input
    confidence: 0.98

⸻

41. Unknown Intent

If Veda cannot reliably determine the Intent, it MUST represent:

UNKNOWN

rather than hallucinating certainty.

Example:

"เอาอันนั้นออกไป"

If “อันนั้น” cannot be grounded:

status: NEEDS_CLARIFICATION
ambiguities:
  - unresolved_reference: "อันนั้น"

⸻

42. Clarification Object

When clarification is required, Veda SHOULD generate a structured clarification request.

Example:

clarification:
  question: "ต้องการลบไฟล์ไหน?"
  reason: "พบไฟล์ที่เป็นไปได้ 3 รายการ"
  candidates:
    - file_a
    - file_b
    - file_c
  consequence_if_wrong: high

The clarification process itself MUST NOT alter the World.

⸻

43. Safety Boundary

Intent interpretation MUST NOT directly execute external actions.

The following is prohibited:

Input
 ↓
Intent Parser
 ↓
Tool Execution

Correct:

Input
 ↓
Intent
 ↓
Goal
 ↓
Plan
 ↓
Authorization
 ↓
Action
 ↓
Verification

⸻

44. No Hidden Escalation

An Intent parser MUST NOT escalate privileges.

For example:

"ช่วยแก้ server"

MUST NOT automatically become:

root shell access

Capability selection and authorization remain separate layers.

⸻

45. Intent Memory

Veda MAY retain Intent history.

However:

Intent ≠ Memory

An Intent represents what someone wanted at a particular point in time.

After completion:

Intent
→ Experience
→ Learning
→ Memory

may occur according to the Learning architecture.

⸻

46. Intent and User Preferences

Preferences MAY influence interpretation.

Example:

User preference:
"prefer local AI"

Input:

"ช่วยวิเคราะห์เอกสารนี้"

Veda MAY choose a local model first.

However, preference MUST NOT override explicit constraints or authorization.

⸻

47. Intent and Model Selection

The Intent Model SHOULD provide semantic requirements to the Intelligence Router.

Example:

intent_requirements:
  reasoning_level: high
  privacy: high
  latency: low
  modality:
    - text

RFC-0016 determines which intelligence provider should be selected.

The Intent Model MUST NOT directly hard-code a model unless explicitly required by policy.

⸻

48. Intent and Planning

Intent defines desired direction.

Goal defines measurable objective.

Plan defines how to achieve it.

Example:

Intent:
"อยากให้ Veda สำรองข้อมูลอัตโนมัติ"
Goal:
"Maintain daily backup of Veda project"
Plan:
1. Identify data
2. Configure storage
3. Schedule backup
4. Test restore
5. Monitor failures

⸻

51. Intent Audit

For every consequential Intent, Veda SHOULD be able to answer:

Who created it?
When?
From what input?
What did Veda infer?
What assumptions were made?
What context was used?
What evidence supported the interpretation?
What ambiguities existed?
What Goal was created?
What Actions resulted?
What authorization allowed those Actions?
What happened afterward?

52. Security Requirements

The Intent subsystem MUST:

1. Preserve actor identity.
2. Preserve raw input when possible.
3. Preserve interpretation provenance.
4. Never grant authority.
5. Never bypass authorization.
6. Record consequential assumptions.
7. Detect unresolved ambiguity.
8. Preserve corrections.
9. Support cancellation.
10. Maintain traceability.
11. Prevent prompt content from silently modifying system policy.
12. Treat external model output as untrusted interpretation until validated.

⸻

53. Privacy Requirements

Intent data MAY contain sensitive information.

Therefore:

Intent
→ Access Control
→ Data Classification
→ Retention Policy

MUST apply.

Sensitive Intent data SHOULD NOT be unnecessarily transmitted to external intelligence providers.

⸻

54. Performance Requirements

Intent processing SHOULD be lightweight for common requests.

Veda SHOULD use staged interpretation:

Fast Parse
   ↓
Cheap Validation
   ↓
Escalate Only If Necessary

Complex reasoning SHOULD only be invoked when:

ambiguity
risk
complexity
unknown context

requires it.

⸻

55. Determinism

For identical:

raw input
+
world state
+
context
+
policy
+
model version

Veda SHOULD produce semantically equivalent Intent representations.

Exact token-level determinism is not required.

Semantic reproducibility is.

⸻

56. Intent Versioning

Intent schema MUST be versioned.

Example:

schema_version: "0.1"
intent_version: 3

Schema evolution MUST preserve compatibility where possible.

Historical Intents MUST remain interpretable.

INT-9

INT-11

60. Fundamental Separation

Veda MUST maintain the following separation:

"I want X"

is an Intent.

"X should become true"

is a Goal.

"Here is how X can become true"

is a Plan.

"Perform operation Y"

is an Action.

"You are permitted to perform Y"

is Authorization.

"Y actually happened"

is an Event/Observation.

"Y produced the expected result"

is Verification.

This separation is one of the central architectural boundaries of Veda.

⸻

61. Design Principle

Veda should not ask only:

“What did the user say?”

It should determine:

What does the user want?
Why?
In what context?
Against which world entities?
Under which constraints?
With what urgency?
With what uncertainty?
What assumptions are required?
What outcome would satisfy the intent?
What authority exists?

Only after these questions are sufficiently resolved should Veda create a Goal.

⸻

62. Final Principle

The Intent layer is the semantic boundary between human desire and machine execution.

The canonical Veda flow is therefore:

Human
  ↓
Input
  ↓
Intent
  ↓
Goal
  ↓
Plan
  ↓
Authorization
  ↓
Action
  ↓
Event
  ↓
World Transition
  ↓
Verification
  ↓
World(t+1)

And the most important invariant is:

INTENT ≠ AUTHORITY

Veda may understand what a human wants without being automatically permitted to do it.
